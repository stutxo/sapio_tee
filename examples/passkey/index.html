Sapio / WASM spending policy

A passkey. A two-key recovery path.

A static Bitcoin wallet: build and verify transactions locally in WASM, authorize normal spends with your passkey and the live enclave, or recover offline with both Bitcoin keys. Review first, authorize second, export last. Nothing is broadcast.

Start with synthetic funding, never real funds.

The default demo UTXO does not exist on-chain. Its signed transaction cannot spend Bitcoin. Manual UTXOs are not checked against a node or chain.

Recovery requires both enrolled Bitcoin private keys, with no timelock and no passkey or enclave approval. Either recovery key alone is insufficient. Keep independent backups of both keys and the public metadata: metadata cannot replace a lost private key or passkey. Recovery protects availability, not against a compromised enclave root. Synced passkeys also depend on their authenticator provider.

What this example does—and does not—prove

Authenticator attestation is not requested: this does not prove which authenticator holds the passkey. Trust this page and its WASM assets to present the correct Bitcoin details; a passkey prompt is not a secure Bitcoin transaction display. The static configuration pins an enclave public identity that the operator must verify through a trusted channel. This page does not independently verify TEE attestation. Normal signing requires the configured HTTPS transport and live enclave; transaction building, response verification, and finalization happen locally. Two-key recovery needs no transport or enclave after the static assets and configuration are loaded.

The policy requires user presence and verification and commits to the whole transaction. It is stateless: an assertion can be replayed for that exact same policy and transaction. It has no expiry or persistent signature counter. This UI requests a fresh assertion for each signing attempt.

Keep the exact HTTPS origin and hostname stable: they are part of this wallet’s policy and passkey relying party. Moving the files to a new origin does not migrate an existing wallet. HTTP is allowed only for explicitly configured localhost development; a local fixture has no hardware TEE assurance.

Enroll or restore

Before creating a passkey, supply two distinct compressed secp256k1 Bitcoin public keys from your recovery signers. Import public metadata to restore an existing address; recovery does not require access to its passkey.

Two-key recovery quorum — both keys required

Each key is 66 hex characters (02 or 03 followed by its 32-byte x coordinate), not a passkey/P-256 key. Repeated keys, including opposite parities of the same key, are rejected. Changing this pair creates a different wallet.

Software-key demonstration, not distributed signing or hardware protection.

This page combines both recovery secrets in one browser for local MuSig2 signing. Use external, independently backed-up keys for a real recovery design; this software demo is not production custody. Generated secrets exist only in the temporary fields below. Back up each separately before closing, cancelling, forgetting, or attempting any signature. They are never automatically saved or exported.

Temporary software recovery private keys

Enter raw 32-byte secp256k1 private keys as 64 hex characters, not WIF. Both must match the enrolled pair, in either order. They are used only after explicit recovery approval in an isolated WASM instance and are never sent over the network. Fields are cleared on every signing attempt, cancellation, and forget. JavaScript strings cannot be reliably erased from browser memory.

Transaction details

Normal spending requires the original passkey and the live enclave through the configured HTTPS signing transport.

Synthetic UTXO: no on-chain funds. The demo recipient is a fixture, not your wallet.

One output sent to the exact receiving address above. The amount must be the actual prevout value. No balance lookup or coin selection is performed.

Checksummed bech32 / bech32m on the configured network; no legacy or wrapped-SegWit addresses. Testnet, testnet4, and signet share an address prefix—verify the intended chain independently.

Amounts are whole satoshis, not BTC. Change returns only to this wallet; dust is rejected, never silently added to the fee. Fees are not estimated.
